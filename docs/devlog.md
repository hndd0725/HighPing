## 11/04 — 아이디어 정하기

- ① 문제: 넷마블네오 AI 인턴십용으로 "AI로 아이디어 → 플레이 가능한 게임"을 만들어야 함
- ② AI와 논의: "코딩하며 어려웠던 것들로 게임을 만들자"는 방향을 본인이 제안 → 서버 개발 중 실제로 겪은 문제들(지연, 타이머 11Hz, 쓰기 큐 상한 등)을 AI에게 주고 게임 안을 여러 개 받음
- ③ 본인 결정: AI 안 1번 "1초 전의 너"를 골라 **"핑이 높을수록 유리한 대전"(고핑)**으로 다듬음. 겪은 문제 → 규칙·아이템 대응표를 만듦 (지연 = 핵심 규칙, 쓰기 큐 3초 상한 = 핑 3초 튕김 등)
- 메모: 아이디어는 AI 안 중에서 고른 것 — "혼자 떠올렸다"고 하지 않기

## 11/05 — 1주차 기획, 클라이언트 그래픽 결정

**1주차 기획 초안**
- ② AI가 초안 작성: 규칙, 서버 구조, 패킷 규약, 일정
- AI가 짚은 문제: "맞히면 핑↑ / 맞으면 핑↓"는 앞선 쪽이 계속 유리해짐(스노우볼) → 플테 질문으로 확인하기로
- 이전 경험을 구조에 반영: 이동은 키 상태만 받고 서버 틱에서 계산 (GH에서 입력 1개당 이동이라 몰아 보내기 문제가 있었음), 인원수 u16 (GH에서 u8이라 256명에서 깨짐)

**2D vs 3D, 어떤 도구로**
- ② AI 첫 추천: SFML 2D (일정 안전) → 본인이 "3D가 더 재밌을 것 같다" → AI가 raylib 3D 추천
- ③ 본인이 바로 받지 않음: "이번 게임 하나로 끝나지 않고 다음에도 쓸 수 있는 기술인지 확인하고 싶다" → OpenGL과 비교 조사 요청
- ② AI 조사 결과
  - 클라이언트 채용 공고에 DirectX/OpenGL 경험이 자격·우대 요건으로 나옴 / 넷마블네오 공고에는 엔진 요구 없음
  - raylib은 OpenGL 위의 추상화 계층(rlgl): 즉시 모드 스타일 함수(rlVertex 등) + 기본 셰이더 + 정해진 이름의 유니폼 자동 연결 → 셰이더·정점 버퍼·행렬 단계를 직접 안 다루게 됨
  - SFML도 OpenGL 위에 만들어져 있고, SFML 3.0.2 문서에 OpenGL 직접 호출과 SFML 그리기를 섞을 수 있다고 적혀 있음(pushGLStates/popGLStates)
- ③ 본인 결정: **SFML(창·입력·글자) + OpenGL 3D 쿼터뷰**. 이유 2개
  1. 렌더링 파이프라인(셰이더, 정점 버퍼, 변환 행렬)을 감추지 않고 직접 다뤄 봄 — 이 개념은 DirectX·엔진 셰이더에도 그대로 이어짐. 지금까지 본인이 직접 짠 렌더링 코드가 없음(GH 렌더링은 팀원 담당)
  2. 이미 쓰는 SFML과 같은 OpenGL 위에서 섞을 수 있음 — 창·입력·글자는 아는 SFML 그대로, 새로 배우는 건 3D 그리기만. raylib은 창·입력까지 자기 것을 써서 SFML을 통째로 바꿔야 함
- 고르지 않은 이유로 쓰면 안 되는 것: "raylib이 느려서" — 캐릭터 2개짜리 게임에선 성능 차이가 이유가 안 됨
- ③ AI가 "11/08까지 안 되면 2D로 전환"하는 포기 기준을 제안 → 본인이 거절: "포기는 안 한다, 부족하면 시간을 더 쓰겠다"

**사격 방식**
- ③ 본인 처음 기준: "실무에서 많이 쓰는 쪽이 좋지 않을까"
- ② AI: 둘 다 실무에서 흔함(히트스캔 = 발로란트·CS2, 투사체 = 롤 스킬샷·배그 저격) → 기준을 "이 게임에 맞는가"로 바꾸자고 제안. 히트스캔은 '유령을 쏘면 빗나감'만 남고 서버 판정이 선 vs 원 1회, 투사체는 탄도 매 틱 이동·충돌·보는 사람별 지연 전송이 추가됨
- ③ 본인 결정: **히트스캔**. 연결점: 실무 히트스캔 서버는 랙 보상(쏜 사람 화면 시점으로 되감아 판정)을 하는데, 고핑은 일부러 되감지 않음

**역할 분담**
- ② AI 안: (가) 전부 본인이 빈칸으로 / (나) 뼈대·반복 코드는 AI 초안 + 본인이 읽고 설명, 핵심 로직만 본인 빈칸
- ③ 본인 결정: (나). 본인 빈칸 = 핑 지연(과거 위치 찾기), 판정, 카메라 행렬, 마우스→바닥 지점. 이유: (가)는 C#·OpenGL을 동시에 처음 배우며 3주 안에 끝내기 어려움, 면접에서 물어볼 핵심은 직접 짜서 설명할 수 있게

## 11/05 (저녁) — 서버 1단계: 스레드 구조

- ① 문제: 클라 2명 접속 → Welcome, Input(키 상태) 받아 60Hz로 이동, 30Hz로 State 전송. 끝 기준 = C# 테스트 클라 2개에서 위치 변화가 찍힘
- ② AI 안 3개: (A) 받은 스레드가 바로 상태 수정 + lock / (B) 수신은 ConcurrentQueue에 넣기만, 게임 루프 1개만 상태를 만짐 / (C) 스레드 1개로 소켓을 돌아가며 확인
- ③ 본인 결정: **B**. 이유: "같은 순간의 실제 위치로 판정"이 핵심 규칙이라 상태를 한 스레드가 틱 단위로 다루는 게 맞음, lock 빠뜨림 버그가 없음. 단점(입력이 다음 틱까지 최대 16.7ms 대기)은 핑을 수백 ms로 다루는 게임이라 작음. GH의 strand와 같은 생각
- ④ 구현: 접속·수신 뼈대는 AI 초안 + 본인이 읽고 설명 (역할 분담표대로). PacketBuffer는 GH_Server_CS 1단계에서 본인이 빈칸을 채운 것을 가져옴
- ④ 1-1 구현 (AI 초안): server/Program.cs(접속 받기), server/Session.cs(Welcome 전송, [2B 길이] → body 수신), tools/TestClient(서버와 같은 PacketBuffer 파일을 링크해서 씀). PacketId는 고핑 규약(Welcome=1 … RoundEnd=6)으로 바꿈
- ⑤ 확인 [측정]: TestClient → `받음 : Welcome myId=1`, Input 2개(`00-03-00-02-01`, `00-03-00-02-00`) 서버에서 `[수신] Input (3바이트)` 2번, 끊으면 `[퇴장]`
- 알고 있는 남은 문제: SendAsync를 여러 스레드가 동시에 부르면 바이트가 섞일 수 있음 → 2단계에서 보내기도 게임 루프 한 곳에서만 하도록
- 검증 (async Task vs async void): AI 설명("안 기다린 Task 예외는 담긴 채 사라진다")을 다른 AI로 교차 확인 → "사라지는 게 아니라 나중에 알게 된다"로 엇갈림 → 실험으로 판정 [측정]: async void 예외 = 프로세스 종료 / async Task 예외 = 서버 유지, GC 후 `TaskScheduler.UnobservedTaskException` 이벤트로 나옴. 결론: RunAsync 안에서 직접 잡아 로그·세션 정리 (2단계에 반영). 이 일로 검증 기준(기획 7-2)을 정함
