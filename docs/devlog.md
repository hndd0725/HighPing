## 11/04 — 아이디어 정하기

- ① 문제: 넷마블네오 AI 인턴십용으로 "AI로 아이디어 → 플레이 가능한 게임"을 만들어야 함
- ② AI와 논의: "코딩하며 어려웠던 것들로 게임을 만들자"는 방향을 본인이 제안 → 서버 개발 중 실제로 겪은 문제들(지연, 타이머 11Hz, 쓰기 큐 상한 등)을 AI에게 주고 게임 안을 여러 개 받음
- ③ 본인 결정: AI 안 1번 "1초 전의 너"를 골라 **"핑이 높을수록 유리한 대전"(고핑)**으로 다듬음. 겪은 문제 → 규칙·아이템 대응표를 만듦 (지연 = 핵심 규칙, 쓰기 큐 3초 상한 = 핑 3초 튕김 등)
- 메모: 아이디어는 AI 안 중에서 고른 것 — "혼자 떠올렸다"고 하지 않기

## 11/05 — 1주차 기획, 클라이언트 그래픽 결정

**1주차 기획 초안**
- ② AI가 초안 작성: 규칙, 서버 구조, 패킷 규약, 일정
- AI가 짚은 문제: "맞히면 핑↑ / 맞으면 핑↓"는 앞선 쪽이 계속 유리해짐(스노우볼) → 플테 질문으로 확인하기로
- 이전 경험을 구조에 반영: 이동은 키 상태만 받고 서버 틱에서 계산 (GH에서 입력 1개당 이동이라 몰아 보내기 문제가 있었음), 인원수 u16 (GH에서 u8이라 256명에서 깨짐)

**2D vs 3D, 어떤 도구로**
- ② AI 첫 추천: SFML 2D (일정 안전) → 본인이 "3D가 더 재밌을 것 같다" → AI가 raylib 3D 추천
- ③ 본인이 바로 받지 않음: "이번 게임 하나로 끝나지 않고 다음에도 쓸 수 있는 기술인지 확인하고 싶다" → OpenGL과 비교 조사 요청
- ② AI 조사 결과
  - 클라이언트 채용 공고에 DirectX/OpenGL 경험이 자격·우대 요건으로 나옴 / 넷마블네오 공고에는 엔진 요구 없음
  - raylib은 OpenGL 위의 추상화 계층(rlgl): 즉시 모드 스타일 함수(rlVertex 등) + 기본 셰이더 + 정해진 이름의 유니폼 자동 연결 → 셰이더·정점 버퍼·행렬 단계를 직접 안 다루게 됨
  - SFML도 OpenGL 위에 만들어져 있고, SFML 3.0.2 문서에 OpenGL 직접 호출과 SFML 그리기를 섞을 수 있다고 적혀 있음(pushGLStates/popGLStates)
- ③ 본인 결정: **SFML(창·입력·글자) + OpenGL 3D 쿼터뷰**. 이유 2개
  1. 렌더링 파이프라인(셰이더, 정점 버퍼, 변환 행렬)을 감추지 않고 직접 다뤄 봄 — 이 개념은 DirectX·엔진 셰이더에도 그대로 이어짐. 지금까지 본인이 직접 짠 렌더링 코드가 없음(GH 렌더링은 팀원 담당)
  2. 이미 쓰는 SFML과 같은 OpenGL 위에서 섞을 수 있음 — 창·입력·글자는 아는 SFML 그대로, 새로 배우는 건 3D 그리기만. raylib은 창·입력까지 자기 것을 써서 SFML을 통째로 바꿔야 함
- 고르지 않은 이유로 쓰면 안 되는 것: "raylib이 느려서" — 캐릭터 2개짜리 게임에선 성능 차이가 이유가 안 됨
- ③ AI가 "11/08까지 안 되면 2D로 전환"하는 포기 기준을 제안 → 본인이 거절: "포기는 안 한다, 부족하면 시간을 더 쓰겠다"

**사격 방식**
- ③ 본인 처음 기준: "실무에서 많이 쓰는 쪽이 좋지 않을까"
- ② AI: 둘 다 실무에서 흔함(히트스캔 = 발로란트·CS2, 투사체 = 롤 스킬샷·배그 저격) → 기준을 "이 게임에 맞는가"로 바꾸자고 제안. 히트스캔은 '유령을 쏘면 빗나감'만 남고 서버 판정이 선 vs 원 1회, 투사체는 탄도 매 틱 이동·충돌·보는 사람별 지연 전송이 추가됨
- ③ 본인 결정: **히트스캔**. 연결점: 실무 히트스캔 서버는 랙 보상(쏜 사람 화면 시점으로 되감아 판정)을 하는데, 고핑은 일부러 되감지 않음

**역할 분담**
- ② AI 안: (가) 전부 본인이 빈칸으로 / (나) 뼈대·반복 코드는 AI 초안 + 본인이 읽고 설명, 핵심 로직만 본인 빈칸
- ③ 본인 결정: (나). 본인 빈칸 = 핑 지연(과거 위치 찾기), 판정, 카메라 행렬, 마우스→바닥 지점. 이유: (가)는 C#·OpenGL을 동시에 처음 배우며 3주 안에 끝내기 어려움, 면접에서 물어볼 핵심은 직접 짜서 설명할 수 있게

## 11/05 (저녁) — 서버 1단계: 스레드 구조

- ① 문제: 클라 2명 접속 → Welcome, Input(키 상태) 받아 60Hz로 이동, 30Hz로 State 전송. 끝 기준 = C# 테스트 클라 2개에서 위치 변화가 찍힘
- ② AI 안 3개: (A) 받은 스레드가 바로 상태 수정 + lock / (B) 수신은 ConcurrentQueue에 넣기만, 게임 루프 1개만 상태를 만짐 / (C) 스레드 1개로 소켓을 돌아가며 확인
- ③ 본인 결정: **B**. 이유: "같은 순간의 실제 위치로 판정"이 핵심 규칙이라 상태를 한 스레드가 틱 단위로 다루는 게 맞음, lock 빠뜨림 버그가 없음. 단점(입력이 다음 틱까지 최대 16.7ms 대기)은 핑을 수백 ms로 다루는 게임이라 작음. GH의 strand와 같은 생각
- ④ 구현: 접속·수신 뼈대는 AI 초안 + 본인이 읽고 설명 (역할 분담표대로). PacketBuffer는 GH_Server_CS 1단계에서 본인이 빈칸을 채운 것을 가져옴
- ④ 1-1 구현 (AI 초안): server/Program.cs(접속 받기), server/Session.cs(Welcome 전송, [2B 길이] → body 수신), tools/TestClient(서버와 같은 PacketBuffer 파일을 링크해서 씀). PacketId는 고핑 규약(Welcome=1 … RoundEnd=6)으로 바꿈
- ⑤ 확인 [측정]: TestClient → `받음 : Welcome myId=1`, Input 2개(`00-03-00-02-01`, `00-03-00-02-00`) 서버에서 `[수신] Input (3바이트)` 2번, 끊으면 `[퇴장]`
- 알고 있는 남은 문제: SendAsync를 여러 스레드가 동시에 부르면 바이트가 섞일 수 있음 → 2단계에서 보내기도 게임 루프 한 곳에서만 하도록
- 검증 (async Task vs async void): AI 설명("안 기다린 Task 예외는 담긴 채 사라진다")을 다른 AI로 교차 확인 → "사라지는 게 아니라 나중에 알게 된다"로 엇갈림 → 실험으로 판정 [측정]: async void 예외 = 프로세스 종료 / async Task 예외 = 서버 유지, GC 후 `TaskScheduler.UnobservedTaskException` 이벤트로 나옴. 결론: RunAsync 안에서 직접 잡아 로그·세션 정리 (2단계에 반영). 이 일로 검증 기준(기획 7-2)을 정함

## 11/09 — 일정 다시 짬, 서버 2단계: 틱 방식

**일정**: 11/06~08 진행 없음 → 약 3일 밀림. 1차 플테 11/14, 2차 11/19, 11/23 제출 유지
- ③ 본인 의견: "선택 기능 한두 개는 있어야 재밌다" → AI가 뺐던 선택 기능을 11/18(1개)·11/20(조건부 1개)에 다시 넣음
- ③ 본인 질문: 혼자 테스트 → 클라우드 서버? → AI: 혼자 테스트에 필요한 건 서버가 아니라 상대 → 간단한 봇을 11/13로 앞당김. 클라우드(리눅스)는 서버 직군 경험으로 가치 있어 11/18 조건부로 넣음

**틱 방식**
- ① 문제: 게임 루프를 1초에 60번 정확히. GH에서 Windows 시계 눈금(15.6ms) 때문에 틱이 늦어졌던 문제가 C#에서도 생기는지
- ② 먼저 측정 [측정, 이 PC 1회]: `Thread.Sleep(16)` 반복 = 2초에 68번(평균 29.8ms) / `PeriodicTimer` = 2초에 125틱(평균 16.0ms, 4% 많음) / 고정 간격 + 따라잡기(C) = 2초에 120틱, 틱 사이 최대 32.3ms
- ② AI 첫 추천: C (이유: P/Invoke라는 새 문법을 피하려고)
- ③ 본인이 짚음: "간격은 B가 고른데 왜 C?" → AI가 다시 봄: B(GH 방식)는 사실 C + 1ms 눈금(timeBeginPeriod(1)) → 측정 [측정]: B = 2초에 120틱, 최대 18.7ms. P/Invoke는 2줄
- ③ 본인 결정: **B**. AI 첫 추천은 배울 양 기준이었고, 기술 기준으로는 B가 나음. timeBeginPeriod는 Windows일 때만 부름(리눅스는 필요 없음)
- ④ 2단계 구현 (AI 초안): GameWorld(ConcurrentQueue<Action> + 전용 스레드 루프, 틱 B, 이동, State 30Hz), Player, Session(받은 패킷은 수신 쪽에서 다 읽고 Post / 보내기는 Channel 하나로 줄 세움, 상한 60개 넘으면 끊음 / 예상 못 한 예외도 [세션 오류]로 로그), TestClient(키 1개를 1초 누르고 뗌)
- ⑤ 확인 [측정]: 틱 = 5000ms 동안 301틱(목표 300). State = 1.5초에 45·46개(30Hz). 이동 = W 1초 → z 0 → -8.00(속도 8m/초 그대로), D 1초 → x -15 → -6.73(8.27m, 약 1.03초분)
- D가 0.27m 더 간 이유 [추정]: 테스트 클라의 `Task.Delay(1000)`이 시계 눈금 때문에 1000ms보다 늦게 끝나 '뗌'이 늦게 도착. 서버 문제인지는 클라가 실제로 뗀 시각을 찍어서 확인할 것

## 11/12 — 서버 2단계 검토 (작성 AI와 검토 AI 분리, 기획 7-3)

- 방법: 서버 코드를 쓴 AI와 별개로, 대화 맥락을 모르는 검토 AI에게 코드와 규약만 주고 읽기 전용으로 검토시킴 (약 1분)
- 찾은 것 4건 → 전부 확인 후 고침
  1. 틱 따라잡기에 상한 없음: 루프가 몇 초 멈췄다 풀리면 밀린 틱이 한꺼번에 돌아 State가 몰려 나가고, 보내기 줄 60개를 넘겨 정상 클라까지 끊김 → 250ms 넘게 밀리면 밀린 틱을 버림
  2. 접속 받는 반복에 예외 처리 없음 (검토 AI는 "재현 조건 불확실"이라고 함) → **실험으로 판정** [측정]: 접속하자마자 강제로 끊기(RST) 300번 → 고치기 전 서버가 첫 번째에서 `SocketException(10054)`로 종료 / 고친 후 접속 실패 289건을 기록하고 계속 동작, 들어온 13명은 입장 13·게임 퇴장 13으로 남는 플레이어 없음, 직후 정상 클라 2개 State 30Hz, 틱 5초 300회
  3. 게임 루프의 job()에 예외 보호 없음 (지금은 터지는 경로 없음, 판정 코드가 들어가면 위험) → job 하나가 예외를 던져도 로그만 찍고 루프는 계속
  4. 정상 퇴장 순간의 Send가 "[끊음] 줄이 가득 참"으로 잘못 찍힘 → 닫힌 경우는 제외
- 검토 AI가 문제없다고 확인한 것: 게임 상태는 루프만 만짐, 퇴장 정리, 패킷 규약과 필드 순서
- 배운 것: 2번은 작성 AI도 본인도 못 본 것. "불확실"이라는 검토 의견을 실험으로 확정한 게 핵심

## 11/12 — 클라이언트 뼈대 (AI 작성)

- ① 문제: 클라이언트를 시작할 틀이 필요함. 오늘 목표 = 창에 3D 바닥이 뜨고 서버에 접속되는 것
- ② 구조 논의 — 빌드 방식: A Visual Studio 프로젝트(.sln + .vcxproj) / B CMake. AI 추천 A (클라는 Windows에서만 돌리고, 이번 주에 CMake를 새로 익힐 시간이 없음)
- ③ 본인 질문: "나중에 리눅스 하려면 B여야 하나? 다른 공고 자격요건에 리눅스가 많다" → AI 답: 리눅스에 올리는 건 서버(C#)라 클라 빌드 방식과 무관. 클라도 필요해지면 CMake 파일만 추가하면 됨(코드는 그대로). C++ 리눅스 빌드 경험이 필요하면 GH_Server를 CMake로 옮기는 쪽이 직접적 → 제출 후 할 일로 미룸

  4. 자기 발밑을 찍으면 판정 없이 연사 간격만 소모 → **고침**: 방향 검사를 연사 간격보다 앞으로

**AI 활용 방식 점검 (본인 요청)**
- 계기: 아는 형의 조언 — "코드부터 시키지 말고, 원하는 기능·문제·방법을 AI가 질문하게 해서 분명히 한 뒤 시켜라. 요즘 AI 활용 능력 검사가 원하는 게 그것"
- 확인: 넷마블네오 공식 "탁월한 인턴, 성장 가이드"를 읽고 지금 방식과 비교. 가이드가 본다고 적은 것 = 과정을 자기 말로 설명 / AI에게 맡긴 일과 내가 판단한 일의 구분 / 왜 그렇게 결정했는지 / AI의 답을 한 번 더 확인 / 기록과 반복 작업의 시스템화. 비용(토큰) 얘기는 없음
- AI의 평가: 기록·검증·역할 구분은 하고 있음. 약한 곳 = 안을 AI가 먼저 내고 본인은 "추천대로"로 고른 결정이 많음(AI를 이끄는 게 아니라 AI가 이끎), 빈칸 4개 중 혼자 푼 건 ④ 하나, 12월 AI 활용 테스트는 혼자 AI를 이끌어야 하는데 그 연습이 안 됨
- 바꾸기로 제안한 것: 다음 기능부터 본인이 먼저 4줄(만들 것 / 규칙·동작 / 모르는 것 / 확인 방법)을 쓰고, AI는 빠진 것만 질문 (본인 답 대기)

**사망·다시 태어남·승리 — 본인이 먼저 정하는 방식으로 진행 (첫 사례)**
- 방식: AI가 안을 내지 않고, 본인이 원하는 동작을 먼저 말함 → AI는 빠진 것만 질문 → 본인이 답 → 구현
- 본인이 처음 쓴 것(그대로): "상대의 hp가 0이 되게 하면 player번호 사망 화면 가운데 위쪽에 뜬다 사망자는 3초뒤에 무작위 위치에 스폰되며 스폰뒤 2초간 무적이되고 풀린다 다시 핑은 다시 원상복구된다"
  - AI가 예상한 것은 "라운드가 끝나고 다시 시작"이었음. 본인 안은 죽어도 계속 이어지는 방식 → 본인 안으로 감
- AI 질문 5개와 본인 답
  1. 원상복구되는 핑은 누구 것? → 죽은 사람만 (200으로)
  2. 게임에 끝이 있나? → 먼저 3번 죽이면 승리
  3. 죽어 있는 3초 동안의 상태? → 내 화면이 회색으로, 주변은 계속 보임
  4. 무적 2초 동안 쏠 수 있나? → 쏠 수 있음
  5. 상대 바로 옆에 태어나도 되나? → 됨 (땅 위이기만 하면)
- 본인이 답하지 않아 AI가 임시로 정한 것 (확인 필요): 죽어 있는 동안은 못 움직이고 못 쏨 / 죽은 사람은 상대 화면에서 사라짐 / 무적인 사람은 밝은 색으로 보임 / 3킬 승리 후에는 "player N 승리"를 3초 띄우고 바로 새 판(킬 0, 처음 자리, HP 3, 핑 200)
- AI가 알아서 처리한 것: HP 3으로 복구, 다시 태어날 때 위치 기록 비움(안 비우면 유령이 죽은 자리에서 새 자리로 미끄러짐), 죽은 상대는 안 맞음(핑이 계속 오르던 함정 차단), 접속 2명 제한(세 번째는 끊음)
- 규약 변경: State의 플레이어 항목에 u8 flags(1=죽음, 2=무적), u8 kills 추가. RoundEnd(winnerId) 사용 시작 (서버·클라·테스트 클라·기획 문서 5번)
- ⑤ 측정 [측정]: 스크립트로 3킬까지 진행 — 3발 → dead·HP 0·킬 +1 / 죽어 있는 동안 쏨 → 변화 없음 / 약 3초 뒤 다른 자리에 다시 태어남, HP 3·핑 200·무적 / 무적 중에 쏨 → HP 3 그대로 / 약 2초 뒤 무적 풀림 / 3킬 → 승자 통보, 둘 다 킬 0·처음 자리 / 세 번째 접속은 끊김
- 아직 못 본 것: 클라 화면(사망 문구, 회색 화면, 승리 문구, 무적 색) — 본인이 눈으로 확인할 것
- 본인이 새로 꺼낸 것 (미결정): ① "진실 리플레이가 꼭 필요한가?" ② "점프가 있어야 한다"

**본인이 넣고 싶다고 한 것 (11/15) — 범위를 정해야 함**
- 본인: 마지막 킬 리플레이는 "나중에 시간 남으면" / 아이템(먹으면 상대 실체가 보임) 넣자 / 점프(총알 피하기용) 넣자 / 1인칭 시점으로 / 나중엔 벽도 / 총알이 나가는 게 보이게(벽에 총알 자국) / 마우스를 꾹 누르면 연속 발사?
- AI: 제출까지 작업일 5일(11/16~20)에 플테·영상·노션·자소서 6문항이 들어 있어 전부는 못 넣음. 1인칭 + 벽 + 점프는 조준 방식·이동·판정·규약이 다 바뀌어 사실상 2판. "제출 전 / 제출 후" 두 목록으로 본인이 자르는 것을 요청 (공식 현직자 글: "범위를 자르는 건 끝까지 사람"). 결정 대기
- 본인 질문: "AI가 짠 코드를 어떻게 봐야 하나 — AI 설명을 듣기 / 내가 찾아보기 / 고친 곳을 알려 달라고 해서 보기" → 공식 현직자 시리즈와 외부 채용 글을 확인: 요즘 보는 것은 "AI가 만든 코드를 읽고 틀린 곳을 잡고 설명하는 능력". 방식 변경 제안: AI는 고친 곳 목록만 주고, 본인이 먼저 읽고 함수마다 한 줄로 적은 뒤 모르는 것만 질문

**본인이 찾은 버그: 원기둥 몸통을 클릭하면 안 맞고, 밑부분을 클릭해야 맞음 (11/15)**
- 본인 관찰: "원통 밑부분 쪽을 클릭해야 맞고, 원통 가운데를 클릭하면 안 맞는 것 같다"
- 원인 [계산, 실행 확인은 본인 몫]: 조준점을 "마우스 직선이 바닥(y = 0)과 만나는 점"으로만 구했음. 비스듬히 내려다보기 때문에 몸통을 클릭하면 그 직선은 몸통을 뚫고 지나 뒤쪽 바닥에 닿음. 본인 카메라(눈 (0, 15, 35))에서 30m 떨어진 상대의 허리 높이(0.9m)를 찍으면 바닥 점이 약 2.2m 뒤 → 쏜 직선이 상대 중심에서 약 2.2m 빗나감(반지름 0.5m)
- 왜 그동안 못 봤나: AI의 측정 스크립트는 좌표를 직접 보내서 "화면에서 클릭"을 안 거침. 검토 AI도 식 자체는 맞다고 확인함. **직접 플레이해야만 보이는 종류의 버그** — 본인이 플레이로 찾음
- 고침 (AI 작성): 원기둥을 높이별로 얇게 잘라(0.2m 간격), 위에서부터 마우스 직선이 그 높이에서 상대 몸통 안을 지나는지 봄. 지나면 그 점이 조준점, 아니면 바닥 점. 본인이 쓴 t 식에 높이(planeY)를 넣어 일반화: `(planeY - nearPoint.y) / (farPoint.y - nearPoint.y)`
- 범위 결정 (본인): 봇 안 만듦(혼자 클라 두 개로 영상 촬영) → 빈 하루에 A 자동 왕복 키(영상에서 유령이 벌어지게 하려면 상대가 움직여야 함) + B 점프(총알 피하기). 1인칭·벽은 제출 후. 핑 3초 튕김은 뺌(죽으면 핑이 200으로 돌아가 3000에 닿을 일이 거의 없음)
- 일하는 순서 정리 (본인 질문 "기존 방식과 달라 어떻게 해야 할지 모르겠다"에 대한 답): 본인이 원하는 것을 말함 → AI는 빠진 것만 질문 → AI가 구현·측정 → AI가 "따라갈 사건 + 정거장 목록"을 줌 → 본인이 30분 읽고 정거장마다 한 줄 + 모르는 줄 → AI가 틀린 곳만 설명 → 본인이 눈으로 확인하고 커밋

**본인이 코드를 읽고 바꾼 규칙 2개 (11/15)**
- 본인이 사망·리스폰 코드를 먼저 읽고 질문 8개 + 규칙 변경 2개를 보냄 (AI가 설명한 뒤가 아니라 읽은 뒤에 나온 것)
- 변경 1 (본인 결정): "맞추면 아무 효과도 없어야 함, 맞으면만 핑이 올라서 날 맞추기 어려워야 함" → 처음 규칙(맞히면 핑↑, 맞으면 핑↓)을 뒤집음. 맞은 쪽 핑 +200, 맞힌 쪽 변화 없음. 11/14에 "플테에서 A/B 비교"로 미뤄 뒀던 것을 본인이 정함. +200이라는 숫자는 AI가 임시로 넣음(확인 필요)
  - 효과: 지는 쪽이 잡기 어려워지는 역전 구조. 최소 핑 100은 이제 닿을 일이 없음(핑이 내려가는 경우가 없어짐)
- 변경 2 (본인 결정): 시작할 때와 새 판에도 스폰 위치를 무작위로 → 입장·다시 태어남·새 판 모두 같은 함수(`RandomSpot`) 사용, 왼쪽/오른쪽 고정 자리 코드는 삭제
- ⑤ 측정 [측정]: 3발 명중 시 핑 쏜 쪽 200 그대로 / 맞은 쪽 200→400→600→800, 죽고 다시 태어나면 200. 입장 위치 (14.3, -3.0)·(-7.4, 6.2)
- 측정에서 보인 것: 새 판 시작 때 두 사람이 (-11.3, -9.4)와 (-10.3, -10.0), 즉 **1.1m 거리**에 태어남. 완전 무작위라 생기는 일 → 최소 거리를 둘지 본인에게 질문
