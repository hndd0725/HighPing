# HIGH PING (고핑) — 1주차 최소판 기획

> 상태: **초안 (11/05)**. `[결정]` 표시는 같이 정할 것. 숫자는 전부 **초기값(가정)** — 측정값 아님, 플테 후 조정.

## 0. 한 줄 소개

상대 화면에 보이는 내 모습이 **내 핑만큼 늦게** 보이는 3D 쿼터뷰 1:1 실시간 대전. (화면은 3D, 움직임은 바닥 평면 위에서만)
맞히면 내 핑이 오르고(더 잡기 어려운 유령), 맞으면 내 핑이 내려간다. 판정은 서버가 **실제 위치**로 한다.

- 아이디어 출처: AI 브레인스토밍 안("1초 전의 너") 중 본인이 골라 다듬음 → 서류·면접에서 "혼자 떠올렸다" 금지
- 서버 C# (.NET 8) / 클라이언트 C++ (SFML 3 창·입력·글자 + OpenGL 3D) / 패킷 규약 = 두 언어 사이의 계약

## 2. 규칙

### 2-1. 맵·이동
- 맵: 바닥 평면 40 × 30 (단위 = 1m), 장애물 없음. 시작 위치 좌/우 끝
- 좌표: GH와 같이 바닥 = (x, z), 높이 y는 안 씀 → 서버 계산은 2D와 똑같음
- 이동: WASD 8방향, 속도 8/초, 반지름 0.5
- `[결정]` 장애물 없이 시작 → 플테에서 "너무 뚫려 있다"면 2주차에 벽 추가

### 2-2. 핑 = 상대에게 보이는 내 지연
- 상대 화면의 나 = **내 핑(ms)만큼 과거의 내 위치**
- 내 화면에는 **"상대가 보고 있는 내 유령"**도 반투명으로 그림 → 유령으로 낚는 심리전이 가능해짐
- 시작 핑 200ms, 범위 0 ~ 3000ms (3000 도달 시 처리는 2주차 '튕김'에서)

### 2-3. 사격·판정
- 마우스 클릭 = 마우스가 가리키는 바닥 지점 방향으로 즉시 레이저(히트스캔), 쿨다운 0.5초
- 판정: 서버가 **받은 순간의 실제 위치**로 레이저 vs 원 충돌 검사
- 내가 쏜 레이저도 상대에겐 **내 핑만큼 늦게** 보임 → "맞고 나서 레이저가 보인다"
- 맞은 결과(HP 감소)는 늦추지 않음
- 히트스캔으로 확정 (11/05). 투사체는 나중에 아이템 후보
- 실무 히트스캔 서버(발로란트·CS 등)는 쏜 사람 화면 시점으로 되감아 판정(랙 보상) → 고핑은 일부러 되감지 않고 현재 실제 위치로 판정

### 2-4. 핑 변화·라운드
- 맞힘: 내 핑 +200 / 맞음: 내 핑 −100
- HP 3, 0이 되면 라운드 끝 → 3초 후 핑·HP·위치 초기화하고 재시작
- `[결정]` **스노우볼 문제**: 맞힌 쪽은 더 안 보이고 맞은 쪽은 더 잘 보임 → 한 번 앞서면 계속 유리. 한 대마다 핑 차이 300ms씩 벌어짐(위 초기값 기준 계산). HP 3이라 라운드가 짧아 괜찮을 수도 있음 → **플테 질문 1번**으로 확인

## 3. 서버 구조 (C#)

```
접속마다 수신 Task (async/await)
     ↓  받은 패킷을 큐에 넣기만 함 (ConcurrentQueue)
게임 루프 스레드 1개 (60Hz)
     ↓  큐 비우기 → 이동 → 판정 → 위치 기록
     ↓  30Hz마다 보는 사람별 State 전송
```

- **게임 상태는 루프 스레드 하나만 만짐** → 락 불필요 (GH의 strand와 같은 생각)
- 위치 기록: 플레이어마다 (서버 시각, x, y)를 틱마다 저장, 최근 3초만 유지
- State 만들기: 보는 사람 B에게 A를 보낼 때 = A 기록에서 `지금 − A.핑` 시점 위치를 찾아 넣음
- 이동은 **키 상태(누르고 있는 키)만 받고 서버 틱에서 계산** → GH에서 입력 1개당 이동이라 생겼던 '몰아 보내기' 문제가 구조적으로 안 생김
- 예상되는 문제: C#의 타이머도 Windows 15.6ms 눈금 영향을 받을 가능성 [추정] → 만들고 나서 틱 횟수부터 잼 (GH에서 했던 방법)

## 4. 클라이언트 구조 (C++ / SFML 3 + OpenGL)

```
SFML    →  창, 키보드·마우스 입력, HUD 글자
OpenGL  →  3D 장면 (바닥, 캐릭터, 레이저)
glad    →  최신 OpenGL 함수 불러오기
glm     →  카메라·좌표 계산 (행렬, 벡터)
```

- 카메라: 쿼터뷰 고정 (비스듬히 내려다봄)
- 그리는 것: 바닥(상자), 나·상대 유령·내 유령(원기둥, 내 유령은 반투명), 레이저(가는 상자)
- 마우스 → 바닥 지점: 마우스 위치에서 카메라 방향으로 선을 쏴 바닥(y=0)과 만나는 점 = 조준점
- 네트워크: Boost.Asio (GH 클라에서 써 본 것) — 수신은 별도 스레드, 메인 루프에서 꺼내 그림
- 내 캐릭터도 서버 State 위치로 그림 (클라 예측 없음, 1주차는 LAN/가까운 거리 전제)
- 상대 위치: 받은 그대로 그림 (보간 없음). 끊겨 보이면 2주차에 보간
- 내 유령: 내 위치 기록에서 `지금 − 내 핑` 시점을 클라가 직접 계산
- 주의: vcpkg SFML은 **3.0.2** — 인터넷 예제 대부분이 2.x라 이벤트 처리 등 문법이 다름
- SFML 3.0.2 문서에 `pushGLStates`/`popGLStates`가 있고 OpenGL 호출과 SFML 그리기를 섞을 수 있다고 적혀 있음 (11/05 문서 확인) → 11/07에 실제로 돌려서 확인
- 3D는 끝까지 감 (본인 결정 11/05). 일정이 밀리면 본인이 시간을 더 씀

## 5. 패킷 규약 (계약)

헤더: `[u16 body 길이][u16 PacketId]`, **빅 엔디안** (GH와 동일). float도 빅 엔디안 4바이트.

| ID | 이름 | 방향 | 내용 |
|---|---|---|---|
| 1 | Welcome | S→C | u32 myId |
| 2 | Input | C→S | u8 keyBits (W=1, A=2, S=4, D=8) — 바뀔 때만 보냄 |
| 3 | Shoot | C→S | f32 aimX, f32 aimZ (바닥 좌표) |
| 4 | State | S→C | u32 serverMs, u16 count, [u32 id, f32 x, f32 z, u16 pingMs, u8 hp] × count |
| 5 | Shot | S→C | u32 shooterId, f32 fromX, fromZ, toX, toZ, u8 hit |
| 6 | RoundEnd | S→C | u32 winnerId |

- 인원수는 처음부터 u16 (GH에서 u8 → 256명에서 깨진 경험)
- C++에서 구조체를 memcpy로 보내지 않음 → 필드 하나씩 쓰고 읽기. C#과 C++이 이 표만 보고 맞아야 함
- C# 쪽 PacketBuffer는 GH_Server_CS 1단계(빈칸 6개)와 같은 형식 → 그걸 끝내면 그대로 가져다 씀

## 7. 역할 분담 (AI 협업 방식) — 확정 11/05 (아래 추천안대로)

넷마블네오가 보는 역량 = **AI와 사람 역할 구분, 워크플로 설계**. 그래서 이 표 자체가 서류 재료.

| 본인 | AI (Claude) |
|---|---|
| 규칙·수치 결정, 플테 판단 | 아이디어 후보, 초안 코드 |
| 패킷 규약(계약) 확정 | 규약대로 C#/C++ 초안 |
| **핵심 로직은 빈칸으로 직접**: 위치 기록에서 과거 위치 찾기, 판정 | C# 문법을 C++과 나란히 설명 |
| **OpenGL도 빈칸으로 직접**: 카메라 행렬, 마우스→바닥 지점 | 셰이더 컴파일·정점 버퍼 같은 반복 코드 초안 |
| 모든 줄 읽고 설명 가능하게, 측정으로 검증 | 버그 원인 후보 제시 |

- 추천: 네트워크·뼈대는 AI 초안 + 본인이 읽고 설명, **게임 규칙의 심장(핑 지연·판정)은 본인 빈칸**

### 7-1. 기능 하나를 만드는 순서 (AI 협업 워크플로)

코드부터 짜지 않고, **구조를 먼저 AI와 이야기하고 본인이 고른 뒤** 만든다.

```
① 문제 정의   — 이 기능이 뭘 해야 하나, 끝났다는 기준은?
     ↓
② 구조 논의   — AI에게 안 2~3개와 장단점을 받음 (예: 과거 위치를 어떻게 저장할까)
     ↓
③ 본인 결정   — 하나를 고르고 이유를 적음. AI 추천과 다르게 고르면 그것도 적음
     ↓
④ 구현        — 역할 분담표대로 (AI 초안 / 본인 빈칸)
     ↓
⑤ 검증        — 측정하거나 직접 플레이. 숫자는 측정값만 기록
     ↓
⑥ 개선        — 문제가 나오면 다시 ①로. "처음 구조 → 문제 → 바꾼 구조"를 남김
```

- 매 기능마다 `docs/devlog.md`에 ①~⑥을 남김 → 자소서·면접·노션에서
  "AI에게 이렇게 물었고 → 구조를 이렇게 정했고 → 이렇게 개선했다"를 그대로 말할 수 있음
- AI가 틀렸거나 본인이 AI 안을 거절한 경우가 제일 좋은 재료 → 빼지 말고 적기

### 7-2. 검증 기준 (AI 말을 무엇으로 확인하나)

AI(다른 AI 포함)의 설명은 **확인할 거리**이지 근거가 아님. 근거는 아래 순서로 센 것.

| 세기 | 근거 | 예 |
|---|---|---|
| 1 | 직접 실행·측정 | async void 실험(프로세스 종료), GetBytes가 리틀 엔디안인지 출력, 봇으로 틱 수 세기 |
| 2 | 공식 문서·원본 소스 | Microsoft Learn, SFML 문서(pushGLStates), raylib rlgl.h |
| 3 | 다른 AI·블로그 | 설명이 서로 다르면 → 1이나 2로 판정 |

- AI가 쓴 코드: 본인이 줄마다 설명 못 하면 커밋 전에 질문
- devlog에는 "무엇으로 확인했나"(실험 결과·문서 링크)를 같이 적음
